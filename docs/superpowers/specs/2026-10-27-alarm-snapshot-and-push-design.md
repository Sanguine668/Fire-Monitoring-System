# 告警画面留存与手机推送设计

- 项目：火情智能监测与预警系统（FireGuard AI）
- 版本：v1.0（2026-10-27）
- 关联文档：《系统设计文档》《告警复核智能体设计》《远距离识别与烟类检测能力升级设计》

## 1. 要解决的问题

当前系统的告警只有一行结构化记录（时间、类型、置信度、累计次数）：

1. **告警无画面证据**，事后无法判断"当时到底拍到了什么"，告警中心只能看文字；
2. **告警只能在本机网页上看到**，人不在电脑前就收不到任何提醒。

本期补两个能力：告警发生时留存画面帧（含检测框），并把新告警推送到手机微信。

## 2. 方案选择

### 2.1 画面帧怎么存

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A | 只存已画框的 JPEG | 最简单、所见即所得；框烧进像素，无法单独取用 |
| B | 只存原始帧 + 框坐标，前端重绘 | 灵活可开关框；需自写 canvas 渲染与坐标缩放，易出错 |
| **C（采用）** | 已画框 JPEG 作主展示 + 框坐标 JSON 留档 | 展示永远正确，同时保留结构化数据 |

### 2.2 推送通道怎么选

系统部署在个人电脑上，没有公网服务器，无法自建推送通道，必须借助第三方服务。评估后采用 **Server酱 Turbo**：

- 免费版每天 5 条，会员 1000 条/天；免费版与会员均限制每分钟 50 条；
- 接口 `POST https://sctapi.ftqq.com/<SendKey>.send`，表单字段 `title` + `desp`；
- 正文为 Markdown，**图片只能是公网 URL，不支持本地文件与 base64**；
- 短信通道需要云厂商账号、签名与模板报备，课程演示不现实，不采用。

## 3. 功能一：告警画面留存

### 3.1 采集时机

检测线程触发告警时，手上已经有画好框的帧（`worker.py` 中 `draw_detections` 之后的 `frame`）与检测结果列表，直接编码落盘，不额外做一次推理。

告警是**合并**的（同一视频源、同一类型未处理时 `count++` 而不新建记录），因此每条告警存两张图：

| 文件 | 含义 | 更新时机 |
| --- | --- | --- |
| `alarm_<id>_first.jpg` | 触发瞬间，告警证据 | 只在新建告警时写入，之后不再变化 |
| `alarm_<id>_latest.jpg` | 最近一次出现的画面 | 每次合并更新时覆盖 |

保存路径：`storage/snapshots/<camera_id>/alarm_<alarm_id>_<variant>.jpg`。

### 3.2 数据模型变更

```sql
ALTER TABLE alarms ADD COLUMN snapshot_first  TEXT;   -- 首帧相对路径
ALTER TABLE alarms ADD COLUMN snapshot_latest TEXT;   -- 最近帧相对路径
ALTER TABLE alarms ADD COLUMN boxes           TEXT;   -- JSON：[{type,confidence,bbox:[x,y,w,h]}]，与检测输出同构
ALTER TABLE alarms ADD COLUMN frame_size      TEXT;   -- "1280x720"，便于日后重绘
```

沿用现有 `init_db()` 的 `PRAGMA table_info` + `ALTER TABLE` 增量迁移方式，不重建表。

### 3.3 前端展示

- 告警中心表格新增缩略图列，显示首帧小图，无图时显示占位；
- 详情抽屉（`el-drawer`）顶部展示大图，可在「触发帧 / 最近帧」间切换；
- 大图下方列出检测结果：类型、置信度、框坐标（来自 `boxes`）；
- 历史告警（功能上线前产生）显示"该告警产生于功能上线前，无画面留存"。

### 3.4 清理策略

- 删除单条告警、清空告警时，同步删除对应图片；
- 服务启动时清理 7 天前的快照目录，避免无限增长；
- 清理失败只记录日志，不阻断启动。

## 4. 功能二：手机推送

### 4.1 触发与去重

用户约定的规则：**服务启动为周期，同一路视频源只推送一次；设置页提供「重置推送记录」**。

- 触发条件：`db.create_alarm` 返回"新建记录"（而非合并更新）时入队；
- 粒度：按视频源去重，**同一路摄像头的明火与烟雾合计只推第一条**；
- 去重实现：数据库原子插入，不依赖内存状态：

```sql
INSERT OR IGNORE INTO alarm_notifications(camera_id, ...) VALUES(...)
-- rowcount = 0 表示该视频源本轮已推送过，直接跳过
```

- 重置：清空 `alarm_notifications`，各视频源恢复可推。

失败处理：**占位即视为已推送**。推送失败不清除占位，避免网络抖动反复消耗额度；失败原因写入记录并在界面展示，需要重来由用户手动重置。

### 4.2 异步执行

推送放在独立后台线程 + `queue.Queue`（有界，满则丢弃并记录日志），检测线程只做 `enqueue`，绝不因 HTTP 超时拖慢推理。线程随 `lifespan` 启动与停止。

### 4.3 消息内容

标题（Server酱 不支持标题换行）：`【火情监测】<视频源名> <明火|烟雾>告警`

正文（Markdown）：

- 监控源、位置、告警类型与等级、置信度、累计次数、时间；
- 告警画面：`![告警画面](http://<本机局域网IP>:8000/api/alarms/<id>/frame?variant=first)`；
- 系统入口链接。

局域网 IP 复用现有 `/api/network` 的挑选逻辑（优先 `192.*`）。**图片仅在手机与电脑同一网络时可见**；取不到局域网 IP 时省略图片行并给出文字说明。

### 4.4 额度保护

免费版每天 5 条，而系统可配置 6 路视频源，理论上会超。因此：

- 内置每日上限（默认 5，可配置），达到后不再发送，只记录"因额度已满跳过"，不报错、不刷屏；
- 发送在线程内串行执行，不并发；单次运行最多推视频源数量条（≤6），远低于每分钟 50 条限制；
- 收到 `code != 0` 或 HTTP 429 时记录原始返回，界面可见。

### 4.5 绑定与配置

采用**单接收人**。配置存 `settings` 表：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `notify_enabled` | 0 | 是否启用推送 |
| `notify_sendkey` | 空 | Server酱 SendKey |
| `notify_name` | 空 | 接收人备注，如"组长手机" |
| `notify_daily_limit` | 5 | 每日发送上限 |

系统设置页新增「告警推送」卡片：启用开关、SendKey（密码框，可显示）、接收人备注、每日上限、**发送测试通知**按钮、**重置推送记录**按钮、推送记录列表（时间/视频源/结果/失败原因）。

## 5. 接口清单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/alarms/{id}/frame?variant=first\|latest` | 返回画面帧 JPEG，缺失返回 404 |
| GET | `/api/alarms/{id}` | 单条告警详情（含解析后的 `boxes`） |
| GET | `/api/notify` | 推送配置（SendKey 掩码）+ 已推送视频源 + 推送记录 |
| PUT | `/api/notify` | 保存启用状态、SendKey、备注、每日上限 |
| POST | `/api/notify/test` | 发送测试通知，返回 Server酱 原始 `code`/`message` |
| POST | `/api/notify/reset` | 清空 `alarm_notifications`，恢复各视频源可推 |

## 6. 安全

- SendKey 等价于接收者的推送凭证：只存本机 SQLite，**不写入仓库、不打印到日志、不出现在提交信息中**；
- 接口返回时掩码（仅显示末 4 位），修改时可整体覆盖；
- 建议对外演示后重新生成 SendKey。

## 7. 测试方式

1. 单元测试：消息渲染（含标题去换行）、按视频源去重、每日上限拦截、缺 SendKey 时跳过、`boxes` 解析；网络层用 monkeypatch 替换，不发真实请求；
2. 集成测试：用演示视频触发一条告警，确认两张图落盘、`GET frame` 返回 200、合并更新时 `latest` 变化而 `first` 不变；
3. 手工验证：点「发送测试通知」，确认微信收到；
4. 真实通道已验证可用（2026-10-27 测试推送返回 `code: 0`、`error: SUCCESS`）。

## 8. 风险与限制

- 免费版额度只有 5 条/天，6 路视频源可能在第 6 路被额度拦截，升级会员或调低源数可解；
- 消息里的画面依赖手机与电脑同一网络，跨网段不显示图片（正文其他信息不受影响）；
- SendKey 明文存于本机数据库，属于单机部署下的可接受取舍；
- 快照占用磁盘，按 7 天清理，长时间不清理会累积；
- 推送"尝试即占位"意味着失败后需手动重置才能重推。

## 9. 本期不做

- 多接收人群发与按人分渠道；
- 短信通道；
- 为功能上线前的历史告警补画面（无源数据）；
- 前端自由缩放、重绘检测框的交互（先展示标注图 + 结构化框列表）。

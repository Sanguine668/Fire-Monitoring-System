## 第一部分　工作任务分解模式介绍

### 一、分解模式的选择

本项目采用**基于项目生命周期的 WBS（工作分解结构）**，并按**自上而下、逐层分解**的方式展开，同时融合**项目阶段划分 + 产品功能模块**的混合分解思路：先按项目生命周期的五个阶段划分大板块，再在技术实现阶段（核心闭环、数据与模型、智能体增强）内部按软件功能模块与 AI 模型模块继续拆解，使分解结果既符合项目管理流程，又能覆盖软件产品本身的功能构成。

该模式适合"AI + Web 工程"类项目：既有需求、文档、验收等管理过程，也有前端页面、后端服务、检测模型、数据集与智能体等并行开发的技术内容。

### 二、层级结构说明

| 层级 | 内容 | 说明 |
| --- | --- | --- |
| 0 级 | 火情智能监测与预警系统 | 项目整体交付物，包含系统、模型与全套文档 |
| 1 级（阶段） | 1 启动与需求、2 核心闭环、3 数据与模型、4 智能体增强、5 收尾交付 | 按项目生命周期划分，对应里程碑管控 |
| 2 级（工作包） | 如 2.1 视频源接入、2.2 实时烟火检测、3.3 远距离与小目标模型 | 可分配到责任人、可独立验收 |
| 3 级（最小工作单元） | 如 2.1.1 本地上传视频、2.1.2 手机 IP Webcam 推流、4.3.1 本地模型量化 | 可直接排期执行、可单独检查完成情况 |

### 三、编号规则

1. 总项目编号为 0；
2. 阶段编号为 1~5；
3. 工作包编号在阶段号后追加序号，如 2.1、2.2、3.3；
4. 最小工作单元在工作包号后继续追加，如 2.1.1、3.3.2、4.3.1；
5. 同一层级编号连续、不跳号，新增任务在末尾追加并记录变更。

### 四、分解原则

1. **100% 覆盖**：五个阶段合起来覆盖项目全部工作，不遗漏、不重复；
2. **可交付导向**：每个工作包都对应明确的交付物或可检查成果；
3. **责任唯一**：一个工作包只设一名责任人，协作成员在分解库中注明；
4. **粒度可控**：最小工作单元控制在 1~5 个工作日内可完成，便于每周跟踪；
5. **文档与产品区分**：管理文档（章程、说明书）与技术交付物（代码、模型、数据集）在分解库中分列，避免混淆验收对象。

### 五、分解模式的优缺点与处理

| 优点 | 说明 |
| --- | --- |
| 流程清晰 | 按生命周期划分阶段，便于设置里程碑、汇报进度 |
| 业务与技术分离 | 需求、开发、模型、增强、交付边界清楚，便于分工 |
| 粒度可控 | 可分解到工作单元，便于分配给前端、后端、算法、文档角色 |
| 突出 AI 特点 | 单列数据、模型与 VLM 智能增强模块，体现项目技术重点 |

| 潜在不足 | 本项目的处理方式 |
| --- | --- |
| 跨阶段依赖（模型输出是核心闭环的输入） | 阶段 2 先用公开基线模型跑通业务闭环并冻结接口契约，阶段 3 完成自训练模型后直接替换，两阶段并行不阻塞 |
| 文档型任务与开发任务并列 | 在分解库中标注"管理文档 / 技术文档"，并明确各阶段的验收对象是文档还是可运行成果 |
| 测试工作不够显性 | 在阶段 2~4 内嵌入单元与联调测试，并在阶段 5 之前单列"测试与验收"工作包（功能测试、缺陷回归、误报与可靠性测试） |
